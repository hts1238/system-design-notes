# Глава 24: S3-подобное объектное хранилище

## Введение

В этой главе мы спроектируем сервис **объектного хранилища**, похожий на **Amazon S3**.

Системы хранения данных делятся на три основные категории:
- **Блочное хранилище**
- **Файловое хранилище**
- **Объектное хранилище**

**Блочные хранилища** — это устройства, появившиеся в 1960-х годах. Примеры таких устройств — HDD и SSD.
Обычно они физически подключены к серверу, хотя могут подключаться и по сети с помощью высокоскоростных сетевых протоколов.
Серверы могут форматировать необработанные блоки и использовать их как файловую систему либо напрямую передавать управление ими другим серверам.

**Файловое хранилище** строится поверх блочного и предоставляет более высокий уровень абстракции, упрощая управление папками и файлами.

**Объектное хранилище** жертвует производительностью ради высокой долговечности, огромного масштаба и низкой стоимости.
Оно предназначено для «холодных» данных и в основном используется для архивирования и резервного копирования.
Иерархической структуры каталогов нет: все данные хранятся в виде объектов в плоской структуре.
По сравнению с другими типами хранилищ оно относительно медленное. Большинство облачных провайдеров предлагают объектные хранилища: Amazon S3, Google GCS и т. д.

</div>

|                 | Блочное хранилище                | Файловое хранилище                      | Объектное хранилище             |
|-----------------|----------------------------------|-----------------------------------------|--------------------------------|
| Изменяемость содержимого | Y                       | Y                                       | N (поддерживается версионирование объектов） |
| Стоимость       | Высокая                          | От средней до высокой                   | Низкая                         |
| Производительность | От средней до высокой, очень высокая | От средней до высокой               | От низкой до средней           |
| Согласованность | Строгая согласованность           | Строгая согласованность                 | Строгая согласованность [5]    |
| Доступ к данным | SAS/iSCSI/FC                     | Стандартный файловый доступ, CIFS/SMB и NFS | RESTful API                 |
| Масштабируемость | Средняя                         | Высокая                                 | Огромная                       |
| Подходит для    | Виртуальных машин (VM), баз данных | Универсального доступа к файловой системе | Двоичных и неструктурированных данных |

Некоторые термины, связанные с объектным хранилищем:
- **Bucket** - логический контейнер для объектов. Его имя глобально уникально.
- **Object** - отдельная единица данных, хранящаяся в bucket. Содержит данные объекта и метаданные.
- **Versioning** - функция, позволяющая хранить несколько вариантов объекта в одном bucket.
- **Унифицированный идентификатор ресурса (URI)** - каждый ресурс однозначно идентифицируется URI.
- **Соглашение об уровне обслуживания (SLA)** - договор между поставщиком услуги и клиентом.

Показатели SLA класса хранения Amazon S3 Standard-Infrequent Access:
- Долговечность 99.999999999% в нескольких зонах доступности
- Данные сохраняются даже при полном уничтожении зоны доступности
- Расчетная доступность — 99.9%

### **Нефункциональные требования**

- **100 PB данных**
- **Долговечность данных на уровне 6 девяток**
- **Доступность сервиса на уровне 4 девяток**
- Эффективность хранения. Снижение стоимости хранения при сохранении высокой надежности и производительности

### **Приблизительная оценка**

Узкими местами объектного хранилища, вероятно, станут емкость дисков или число операций ввода-вывода в секунду (IOPS).

Предположения:
- 20% объектов маленькие (менее 1mb), 60% среднего размера (1-64mb), а 20% большие (более 64mb),
- один жесткий диск (SATA, 7200rpm) способен выполнять 100-150 произвольных поисковых операций в секунду (100-150 IOPS)

Исходя из этих предположений, можно оценить общее количество объектов, которые система сможет хранить.
- Для упрощения вычислений возьмем медианный размер для каждого типа объектов: 0.5mb для маленьких, 32mb для средних и 200mb для больших.
- При объеме хранилища 100PB (10^11 MB) и использовании 40% емкости получим 0,68 млрд объектов
- Если предположить, что метаданные занимают 1kb, для их хранения потребуется 0.68tb

## Шаг 2: Предложение высокоуровневого проекта и согласование

Прежде чем перейти к проектированию, рассмотрим несколько интересных свойств объектного хранилища:
- **Неизменяемость объектов** - объекты в объектном хранилище неизменяемы (в отличие от других систем хранения). Их можно удалить или заменить, но нельзя обновить.
- **Хранилище «ключ-значение»** - URI объекта служит его ключом, а получить содержимое можно HTTP-запросом
- **Однократная запись и многократное чтение** - данные записываются один раз и читаются много раз. Согласно некоторому исследованию Linkedin, 95% операций — чтение
- Поддержка как маленьких, так и больших объектов

Принцип работы объектного хранилища похож на UNIX: при сохранении файла его имя записывается в структуру данных inode, а содержимое файла размещается в разных местах диска.
В inode содержится список указателей на блоки файла, расположенные в разных местах диска.

При обращении к файлу сначала из inode считываются его метаданные, а затем содержимое.

Объектное хранилище работает аналогичным образом: для сведений о файле используется хранилище метаданных, а содержимое хранится на диске:

### **Высокоуровневая архитектура**

<div style="margin-left:3rem">
    <img src="./images/high-level-design.png" alt="высокоуровневая архитектура объектного хранилища" width="500" />

- **Балансировщик нагрузки** - распределяет запросы API между репликами сервиса
- **Сервис API** - сервер без состояния, координирующий вызовы хранилища метаданных, объектного хранилища и сервиса IAM.
- **Управление идентификацией и доступом (IAM)** - централизованное управление аутентификацией, авторизацией и контролем доступа.
- **Хранилище данных** - хранит и извлекает фактические данные. Операции выполняются по ID объекта (UUID).
- **Хранилище метаданных** - хранит метаданные объектов

### **Загрузка объекта**

<div style="margin-left:3rem">
    <img src="./images/uploading-object.png" alt="загрузка объекта" width="500" />
</div>

- Создается bucket с именем "bucket-to-share" с помощью HTTP PUT-запроса
- Сервис API обращается к IAM, чтобы проверить авторизацию пользователя и наличие прав на запись
- Сервис API обращается к хранилищу метаданных для создания записи bucket. После создания возвращается успешный ответ.
- После создания bucket отправляется HTTP PUT для создания объекта с именем "script.txt"
- Сервис API проверяет личность пользователя и наличие прав на запись
- После успешной проверки содержимое объекта передается в хранилище данных через HTTP PUT. Хранилище сохраняет его и возвращает UUID.
- Сервис API обращается к хранилищу метаданных, чтобы создать запись с object_id, bucket_id, bucket_name и другими метаданными.

Пример запроса на загрузку объекта:

```
PUT /bucket-to-share/script.txt HTTP/1.1
Host: foo.s3example.org
Date: Sun, 12 Sept 2021 17:51:00 GMT
Authorization: authorization string
Content-Type: text/plain
Content-Length: 4567
x-amz-meta-author: Alex

[4567 bytes of object data]
```

### **Скачивание объекта**

У bucket нет иерархии каталогов, но можно создать логическую иерархию, объединив имя bucket и имя объекта, чтобы имитировать структуру папок.

Пример GET-запроса для получения объекта:

```
GET /bucket-to-share/script.txt HTTP/1.1
Host: foo.s3example.org
Date: Sun, 12 Sept 2021 18:30:01 GMT
Authorization: authorization string
```

<div style="margin-left:3rem">
    <img src="./images/download-object.png" alt="скачивание объекта" width="500" />
</div>

- Клиент отправляет HTTP GET-запрос балансировщику нагрузки, то есть `GET /bucket-to-share/script.txt`
- Сервис API запрашивает IAM, чтобы проверить наличие у пользователя прав на чтение bucket
- После проверки UUID объекта извлекается из хранилища метаданных
- Содержимое объекта извлекается из хранилища данных по UUID и возвращается клиенту

Сервис маршрутизации данных предоставляет RESTful или gRPC API для доступа к кластеру узлов данных.

Его основные обязанности:
- запрашивать у сервиса размещения подходящий узел данных для хранения данных
- считывать данные с узлов данных и возвращать их сервису API
- записывать данные на узлы данных

Сервис размещения определяет, на каких узлах данных следует хранить объект.
Он поддерживает виртуальную карту кластера, описывающую физическую топологию кластера.

<div style="margin-left:3rem">
    <img src="./images/virtual-cluster-map.png" alt="виртуальная карта кластера" width="500" />
</div>

Сервис также отправляет сигналы проверки работоспособности всем узлам данных, чтобы определять, следует ли исключить их из виртуального кластера.

Поскольку это критически важный сервис, рекомендуется поддерживать кластер из 5 или 7 реплик, синхронизируемых с помощью алгоритмов консенсуса Paxos или Raft.
Например, кластер из 7 узлов может выдержать отказ 3 узлов.

Узлы данных хранят фактические данные объектов.
Надежность и долговечность обеспечиваются репликацией данных на несколько узлов.

На каждом узле данных работает демон, отправляющий сигналы проверки работоспособности сервису размещения.

Сигнал содержит следующие сведения:
- Сколько дисков (HDD или SSD) обслуживает узел данных?
- Какой объем данных хранится на каждом диске?

#### Организация данных

Один из простых способов управления данными — хранить каждый объект в отдельном файле.

Это работает, но при большом количестве маленьких файлов файловая система будет работать неэффективно:
- Блоки данных на HDD расходуются впустую, поскольку каждый файл занимает блок целиком. Типичный размер блока — 4kb.
- Большое количество файлов означает большое количество inode. Операционные системы плохо работают с чрезмерным числом inode, кроме того, их количество ограничено.

Эти проблемы можно решить, объединяя множество маленьких файлов в более крупные с помощью журнала предварительной записи (WAL). Когда файл достигает предельного размера (обычно несколько GB), создается новый файл:

<div style="margin-left:3rem">
    <img src="./images/wal-optimization.png" alt="оптимизация хранения с помощью WAL" width="500" />
</div>

Недостаток этого подхода в том, что доступ на запись к файлу нужно сериализовать. Несколько ядер, обращающихся к одному файлу, должны ждать друг друга.
Чтобы решить эту проблему и избежать конкуренции за блокировки, можно закрепить файлы за определенными ядрами.

#### Поиск объектов

Чтобы поддержать хранение нескольких объектов в одном файле, нужно вести таблицу со следующими данными для узла данных:
- `object_id`
- `filename` — имя файла, в котором хранится объект
- `file_offset` — смещение, с которого начинается объект
- `object_size`

Эту таблицу можно разместить в файловой БД, например RocksDB, или в традиционной реляционной базе данных.
Поскольку нагрузка на запись невелика, а на чтение велика, лучше подойдет реляционная база данных.

Как ее развернуть?
Можно разместить БД в отдельном кластере, масштабировать независимо и предоставить доступ всем узлам данных.

Недостатки:
- для обработки всех запросов кластер придется активно масштабировать
- между узлом данных и кластером БД возникнет дополнительная сетевая задержка

В качестве альтернативы можно воспользоваться тем, что узлам данных нужны только относящиеся к ним данные,
и разместить реляционную БД непосредственно на самом узле данных.

SQLite — хороший вариант, поскольку это легковесная файловая реляционная база данных.

#### Долговечность данных

Долговечность данных — важное требование нашего проекта. Чтобы достичь уровня в 6 девяток, нужно тщательно рассмотреть все возможные случаи отказа.

Первая проблема, которую нужно решить, — аппаратные сбои. Для этого можно реплицировать узлы данных, снижая вероятность отказа.
Кроме того, реплики следует распределить по разным доменам отказа (между стойками, ЦОД, отдельными сетями и т. д.).
Критическое событие может вызвать несколько аппаратных сбоев в одном домене:

<div style="margin-left:3rem">
    <img src="./images/failure-domain-isolation.png" alt="изоляция доменов отказа" width="500" />
</div>

Если годовая частота отказов типичного HDD составляет 0.81%, создание трех копий обеспечит долговечность на уровне 6 девяток.

Такая репликация узлов данных обеспечивает нужную долговечность, но для снижения затрат на хранение можно также использовать кодирование с исправлением стираний.

Кодирование с исправлением стираний позволяет использовать биты четности для восстановления утраченных битов в случае сбоя:

<div style="margin-left:3rem">
    <img src="./images/erasure-coding.png" alt="кодирование с исправлением стираний" width="500" />
</div>

Представим, что эти биты — узлы данных. Если два из них выйдут из строя, их можно восстановить по оставшимся четырем.

Существует несколько схем кодирования с исправлением стираний. В нашем случае можно применить схему 8+4, распределив данные по разным доменам отказа для максимальной надежности:

<div style="margin-left:3rem">
    <img src="./images/erasure-coding-across-failure-domains.png" alt="кодирование с исправлением стираний в разных доменах отказа" width="500" />
</div>

Кодирование с исправлением стираний позволяет значительно снизить стоимость хранения (на 50%), но уменьшает скорость доступа, поскольку сервису маршрутизации данных приходится собирать данные из нескольких мест:

<div style="margin-left:3rem">
    <img src="./images/erasure-coding-vs-replication.png" alt="сравнение кодирования с исправлением стираний и репликации" width="500" />
</div>

Другие особенности:
- Для репликации требуется 200% дополнительных затрат на хранение (при 3 репликах), а для кодирования с исправлением стираний — 50%
- Кодирование с исправлением стираний [обеспечивает долговечность на уровне 11 девяток](https://github.com/Backblaze/erasure-coding-durability), тогда как репликация — на уровне 6 девяток
- Для кодирования с исправлением стираний требуются дополнительные вычисления для расчета и хранения битов четности

В итоге репликация больше подходит приложениям, чувствительным к задержкам, а кодирование с исправлением стираний привлекательно своей экономичностью и долговечностью.
Кроме того, кодирование с исправлением стираний гораздо сложнее реализовать.

#### Проверка корректности

### **Модель метаданных**

Схемы таблиц:

<div style="margin-left:3rem">
    <img src="./images/metadata-data-model.png" alt="модель данных метаданных" width="500" />
</div>

Нужно поддерживать следующие запросы:
- Найти ID объекта по имени
- Добавить или удалить объект по имени
- Вывести список объектов в bucket с одинаковым префиксом

Обычно число bucket, которые может создать пользователь, ограничено, поэтому таблица bucket невелика и может поместиться на одном сервере БД.
Тем не менее сервер нужно масштабировать для обеспечения пропускной способности чтения.

Однако таблица объектов, скорее всего, не поместится на одном сервере базы данных. Поэтому ее можно масштабировать с помощью шардинга:
- Шардинг по bucket_id приведет к проблемам с горячими точками, поскольку в одном bucket могут находиться миллиарды объектов
- Шардинг по bucket_id обеспечивает более равномерное распределение нагрузки, но запросы будут медленными
- Мы выберем шардинг по `hash(bucket_name, object_name)`, поскольку большинство запросов основано на имени объекта или bucket.

Однако даже при такой схеме шардинга вывод списка объектов в bucket будет медленным.

### **Вывод списка объектов в bucket**

В одной базе данных список объектов по префиксу (похожему на каталог) формируется так:

```
SELECT * FROM object WHERE bucket_id = "123" AND object_name LIKE `abc/%`
```

Выполнить такой запрос в базе данных с шардингом сложно. Для этого можно запустить запрос на каждом шарде и объединить результаты в памяти.
Однако это усложняет пагинацию: на разных шардах разное число результатов, поэтому для каждого нужно отдельно поддерживать limit/offset.

Можно учесть, что объектные хранилища обычно не оптимизированы для вывода списков объектов, и пожертвовать его производительностью.
Кроме того, можно создать денормализованную таблицу для вывода списка объектов, разделенную по ID bucket.
Тогда запрос списка будет достаточно быстрым, поскольку он выполняется на одном экземпляре базы данных.

### **Оптимизация загрузки больших файлов**

Загрузку больших файлов можно оптимизировать с помощью составной загрузки: большой файл разделяется на несколько фрагментов, которые загружаются независимо:

<div style="margin-left:3rem">
    <img src="./images/multipart-upload.png" alt="составная загрузка файла" width="500" />
</div>

- Клиент вызывает сервис для начала составной загрузки
- Хранилище данных возвращает upload ID, уникально идентифицирующий загрузку
- Клиент разделяет большой файл на несколько фрагментов, которые независимо загружаются с использованием upload id
- После загрузки фрагмента хранилище данных возвращает etag — контрольную сумму md5, идентифицирующую этот фрагмент
- После загрузки всех частей клиент отправляет запрос на завершение составной загрузки, содержащий upload_id, номера частей и все etag
- Хранилище данных собирает объект из его частей. Это может занять несколько минут. После завершения клиент получает успешный ответ.

На этом этапе можно удалить старые ненужные части. Для этого можно добавить сборщик мусора.

### **Сборка мусора**

Сборка мусора — это процесс освобождения больше не используемого пространства хранения. Данные могут стать мусором по нескольким причинам:
- **отложенное удаление объекта** - объект помечается удаленным, но фактически не удаляется
- **осиротевшие данные** - например, загрузка прервалась, и старые части нужно удалить
- **поврежденные данные** - данные, не прошедшие проверку контрольной суммы

Сборщик мусора также отвечает за освобождение неиспользуемого места в репликах.
При репликации данные удаляются как из основных узлов, так и из реплик. При кодировании с исправлением стираний (8+4) данные удаляются со всех 12 узлов.

Чтобы упростить удаление, мы будем использовать процесс, называемый компактизацией:
- Сборщик мусора копирует неудаленные объекты из "data/b" в "data/d"
- После завершения копирования таблица `object_mapping` обновляется в рамках транзакции базы данных
- Чтобы не создавать слишком много маленьких файлов, компактизация выполняется для файлов, превысивших определенный пороговый размер
