# Глава 8: Проектирование сервиса сокращения URL

## Введение
В этой главе рассматривается проектирование сервиса сокращения URL, такого как TinyURL. Основные цели системы: **сокращение URL**, **перенаправление** и **высокая масштабируемость** для обработки большого трафика.

### Требования
- Сокращённые URL должны быть **уникальными** и **как можно короче**.
- Обработка **100 миллионов генераций URL в день** с расчётом на 10 лет работы.
- Поддержка **эффективных операций чтения** при соотношении чтения и записи 10:1.
- Хранение 365 миллиардов записей, для чего за 10 лет потребуется около **365 TB**.

---

## Шаг 1: Высокоуровневое проектирование

### Конечные точки API
1. **Сокращение URL:**
   - Конечная точка: `POST api/v1/data/shorten`
   - Параметры: `{longUrl: longURLString}`
   - Возвращает: `shortURL`

2. **Перенаправление URL:**
   - Конечная точка: `GET api/v1/shortUrl`
   - Возвращает `longURL` для перенаправления.

    <p align="center">
    <img src="./images/url-redirection.png" alt="Перенаправление URL" width="600">
    </p>

### Перенаправление URL
- **Перенаправление 301:** означает, что запрошенный URL «постоянно» перемещён на длинный URL. Браузер кэширует ответ,
и последующие запросы того же URL не отправляются в сервис сокращения URL.
- **Перенаправление 302:** временное; полезно для аналитики, например для отслеживания переходов.

### Сокращение URL
<p align="center">
    <img src="./images/url-shortening.png" alt="Сокращение URL" width="400">
</p>

- Используйте **хеш-функцию** для генерации короткого URL, преобразуя длинные URL в уникальные сокращённые варианты.
- Хеш-функция должна удовлетворять следующим требованиям:
    - Для каждого longURL должно вычисляться одно значение hashValue.
    - По каждому hashValue можно восстановить longURL.

## Шаг 2: Подробное проектирование

### Модель данных
Храните соответствия `<shortURL, longURL>` в реляционной базе данных, чтобы оптимизировать использование памяти. Схема таблицы включает:
- `id` (первичный ключ),
- `shortURL`,
- `longURL`.

    <img src="./images/table-schema.png" alt="Схема таблицы" width="300">

### Хеш-функция
#### 1. Преобразование в систему счисления по основанию 62:
- Кодирует числа с помощью символов `[0-9, a-z, A-Z]`, предоставляя **62 возможных символа**.
- Преобразование системы счисления является ещё одним распространённым подходом к сокращению URL.
- Короткому URL можно присвоить уникальный идентификатор и преобразовать его в систему счисления по основанию 62, чтобы получить короткий URL.
- Семисимвольный хеш поддерживает до **3,5 триллиона уникальных URL**, чего достаточно для 365 миллиардов URL.

**Пример:**
Преобразуем ID `2009215674938` в систему счисления по основанию 62:
- `2009215674938` → `zn9edcu`.

#### 2. Хеширование и разрешение коллизий:
- Используйте такие хеш-функции, как CRC32, MD5 или SHA-1.

    <img src="./images/hash-function.png" alt="Хеш-функция" width="500">

- Один из подходов заключается в том, чтобы взять первые 7 символов хеш-значения, однако это может привести к коллизиям.
- Чтобы разрешить коллизии, рекурсивно добавляйте новую заранее заданную строку, пока коллизии не исчезнут, но это может быть затратным.
- Для эффективного поиска используйте **фильтры Блума**, чтобы разрешать коллизии.

    <p align="center">
    <img src="./images/url-lookup.png" alt="Поиск URL" width="500">
    </p>

### Сравнение

- **Хеширование и разрешение коллизий:**
    - Фиксированная длина короткого URL.
    - Генератор уникальных идентификаторов не требуется.
    - Возможны коллизии, которые необходимо разрешать.
    - Нельзя найти следующий доступный короткий URL, поскольку он не зависит от ID.

- **Преобразование в систему счисления по основанию 62**
    - Длина не фиксирована и увеличивается вместе с ID.
    - Требуется генератор уникальных идентификаторов.
    - Коллизии невозможны.
    - Следующий короткий URL легко найти, если ID увеличивается на 1 (это может быть проблемой безопасности).

### Процесс сокращения URL

<p align="center">
    <img src="./images/url-shortening-flow.png" alt="Процесс сокращения URL" width="500">
</p>

1. Проверьте, есть ли `longURL` в базе данных.
2. Если есть, верните существующий `shortURL`.
3. В противном случае:
   - Сгенерируйте уникальный ID с помощью **распределённого генератора идентификаторов**.
   - Преобразуйте ID в `shortURL` в системе счисления по основанию 62.
   - Сохраните соответствие `<id, shortURL, longURL>` в базе данных.



---

### Процесс перенаправления URL
<p align="center">
    <img src="./images/url-redirecting-flow.png" alt="Процесс перенаправления URL" width="600">
</p>

1. Пользователь переходит по `shortURL`.
2. Выполните поиск соответствия `<shortURL, longURL>`:
   - Сначала проверьте **кэш** для ускорения доступа.
   - Если соответствия нет в кэше, обратитесь к базе данных.
3. Перенаправьте пользователя на `longURL`.

## Дополнительные аспекты
### Ограничитель частоты запросов
- Предотвращайте злоупотребления, ограничивая количество запросов с одного IP.

### Масштабируемость
1. **Уровень веб-серверов:** без сохранения состояния; масштабируется добавлением и удалением веб-серверов.
2. **Уровень базы данных:** используйте репликацию и шардирование.

### Аналитика
- Собирайте данные о количестве переходов, источниках и времени для получения бизнес-аналитики.

### Высокая доступность и надёжность
- Обеспечьте согласованную и надёжную работу сервисов с помощью репликации базы данных и отказоустойчивого проектирования.
