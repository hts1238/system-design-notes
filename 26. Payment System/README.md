# Глава 26: Платёжная система

## Введение
В этой главе спроектируем **платёжную систему**, лежащую в основе современной **электронной коммерции**.

**Платёжная система** предназначена для проведения финансовых операций и перевода денежных средств.

---

## Шаг 1: Разберёмся в задаче и определим рамки проектирования
 * C: Какую платёжную систему мы проектируем?
 * I: Платёжный бэкенд для системы электронной коммерции, например Amazon.com. Он отвечает за все операции по переводу денег.
 * C: Какие способы оплаты поддерживаются: кредитные карты, PayPal, банковские карты и т. д.?
 * I: В реальной системе нужно поддерживать все эти способы. Для собеседования ограничимся оплатой кредитными картами.
 * C: Мы самостоятельно обрабатываем платежи по кредитным картам?
 * I: Нет, мы используем стороннего провайдера, например Stripe, Braintree или Square.
 * C: Мы храним данные кредитных карт в своей системе?
 * I: Из-за требований соответствия мы не храним данные кредитных карт непосредственно в своих системах. Мы полагаемся на сторонних платёжных провайдеров.
 * C: Приложение работает по всему миру? Нужно ли поддерживать разные валюты и международные платежи?
 * I: Приложение глобальное, но для целей собеседования предположим, что используется только одна валюта.
 * C: Сколько платёжных транзакций в день должна поддерживать система?
 * I: 1 млн транзакций в день.
 * C: Нужно ли поддерживать выплаты, например ежемесячные выплаты продавцам?
 * I: Да, это необходимо.
 * C: Есть ли ещё что-то, на что стоит обратить внимание?
 * I: Нужно поддерживать сверку данных, чтобы устранять несоответствия при взаимодействии с внутренними и внешними системами.

### **Функциональные требования**
 * Приём платежей — платёжная система получает деньги от покупателей от имени продавцов.
 * Выплаты — платёжная система отправляет деньги продавцам по всему миру.

### **Нефункциональные требования**
 * Надёжность и отказоустойчивость. Необходимо аккуратно обрабатывать неуспешные платежи.
 * Необходимо настроить сверку между внутренними и внешними системами.

### **Приблизительная оценка**
Система должна обрабатывать 1 млн транзакций в день, то есть 10 транзакций в секунду.

Для любой базы данных это невысокая пропускная способность, поэтому в рамках собеседования она не будет главным предметом обсуждения.

### **Приём платежей**
Вот схема приёма платежа на верхнем уровне:

<div style="margin-left:3rem">
    <img src="./images/payin-flow-high-level.png" alt="схема приёма платежа верхнего уровня" width="500" />
</div>

 * Платёжный сервис — принимает события платежей и координирует процесс оплаты. Обычно он также проверяет риски через стороннего провайдера, выявляя нарушения требований AML и возможную преступную деятельность.
 * Исполнитель платежей — проводит отдельный платёжный ордер через платёжного провайдера (PSP). Событие платежа может содержать несколько платёжных ордеров.
 * Платёжный провайдер (PSP) — переводит деньги с одного счёта на другой, например со счёта кредитной карты покупателя на банковский счёт сайта электронной коммерции.
 * Платёжные системы — организации, обрабатывающие операции по кредитным картам, например Visa и MasterCard.
 * Главная книга — ведёт финансовый учёт всех платёжных транзакций.
 * Кошелёк — хранит балансы счетов всех продавцов.

Пример процесса приёма платежа:
 * Пользователь нажимает «Оформить заказ», и платёжный сервис получает событие платежа.
 * Платёжный сервис сохраняет событие в своей базе данных.
 * Платёжный сервис вызывает исполнителя для обработки всех платёжных ордеров, входящих в это событие.
 * Исполнитель платежей сохраняет платёжный ордер в своей базе данных.
 * Исполнитель платежей вызывает внешнего PSP для обработки платежа по кредитной карте.
 * После обработки платежа исполнитель сообщает платёжному сервису, который обновляет кошелёк, фиксируя сумму средств продавца.
 * Сервис кошелька сохраняет обновлённый баланс в своей базе данных.
 * Платёжный сервис вызывает главную книгу, чтобы зарегистрировать все движения средств.

### **API платёжного сервиса**
```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```

Пример `payment_order`:
```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```

Примечания:
 * `payment_order_id` передаётся PSP для дедупликации платежей, то есть служит ключом идемпотентности.
 * Поле amount имеет тип `string`, поскольку `double` не подходит для представления денежных сумм.

```
GET /v1/payments/{:id}
```

Эта конечная точка возвращает статус выполнения отдельного платежа по `payment_order_id`.

### **Модель данных платёжного сервиса**
Нужно поддерживать две таблицы: `payment_events` и `payment_orders`.

Для платёжных систем производительность обычно не является главным фактором, зато важна строгая согласованность.

Другие критерии выбора базы данных:
 * Широкий рынок специалистов DBA, которых можно нанять для администрирования базы данных.
 * Проверенная репутация: база данных используется другими крупными финансовыми организациями.
 * Богатая экосистема вспомогательных инструментов.
 * Предпочтение традиционной SQL-базе перед NoSQL/NewSQL благодаря гарантиям ACID.

Таблица `payment_events` содержит:
 * `checkout_id` - string, первичный ключ
 * `buyer_info` - string (заметка автора: вероятно, уместнее использовать внешний ключ на другую таблицу)
 * `seller_info` - string (заметка автора: см. предыдущую заметку)
 * `credit_card_info` - зависит от провайдера кредитных карт
 * `is_payment_done` - boolean

Таблица `payment_orders` содержит:
 * `payment_order_id` - string, первичный ключ
 * `buyer_account` - string
 * `amount` - string
 * `currency` - string
 * `checkout_id` - string, внешний ключ
 * `payment_order_status` - enum (`NOT_STARTED`, `EXECUTING`, `SUCCESS`, `FAILED`)
 * `ledger_updated` - boolean
 * `wallet_updated` - boolean

Примечания:
 * Одному событию платежа может соответствовать много платёжных ордеров.
 * Для приёма платежа поле `seller_info` не требуется. Оно нужно только для выплат.
 * Поля `ledger_updated` и `wallet_updated` обновляются при вызове соответствующих сервисов для регистрации результата платежа.
 * Переходами состояния платежей управляет фоновая задача: она проверяет обновления незавершённых платежей и отправляет оповещение, если платёж не обработан за разумное время.

### **Система учёта методом двойной записи**
Учёт методом двойной записи — основа любой платёжной системы. Движение средств фиксируется одновременно на двух счетах: баланс одного увеличивается (кредит), а другого уменьшается (дебет):

| Счёт | Дебет | Кредит |
|---------|-------|--------|
| покупатель | $1 |        |
| продавец   |    | $1     |

Сумма всех проводок всегда равна нулю. Этот механизм обеспечивает сквозную отслеживаемость всех движений средств в системе.

Компоненты процесса выплаты очень похожи на компоненты процесса приёма платежа.

## Шаг 3: Подробный разбор архитектуры
В этом разделе рассмотрим, как сделать систему быстрее, надёжнее и безопаснее.

### **Интеграция с PSP**
Если наша система может напрямую подключаться к банкам или платёжным системам, проводить платежи можно без PSP.
Такие подключения встречаются редко и обычно используются крупными компаниями, которые могут оправдать соответствующие инвестиции.

При традиционном подходе интегрировать PSP можно одним из двух способов:
 * Через API, если наша платёжная система может собирать платёжные данные.
 * Через платёжную страницу провайдера, чтобы не заниматься соблюдением требований к платёжной информации.

Вот как работает процесс оплаты через платёжную страницу провайдера:

<div style="margin-left:3rem">
    <img src="./images/hosted-payment-page-workflow.png" alt="процесс оплаты через платёжную страницу провайдера" width="500" />
</div>

 * Пользователь нажимает в браузере кнопку «К оформлению заказа».
 * Клиент передаёт платёжному сервису сведения о платёжном ордере.
 * Получив данные платёжного ордера, платёжный сервис отправляет PSP запрос на регистрацию платежа.
 * PSP получает сведения о платеже, например валюту, сумму и срок действия, а также UUID для обеспечения идемпотентности. Обычно это UUID платёжного ордера.
 * PSP возвращает токен, уникально идентифицирующий зарегистрированный платёж. Токен сохраняется в базе данных платёжного сервиса.
 * После сохранения токена пользователю показывается размещённая у PSP платёжная страница. Она инициализируется с помощью токена и URL для перенаправления при успехе или ошибке.
 * Пользователь вводит платёжные данные на странице PSP, провайдер обрабатывает платёж и возвращает его статус.
 * Затем пользователь перенаправляется обратно на redirectURL. Пример URL перенаправления: `https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * Асинхронно PSP вызывает платёжный сервис через webhook, чтобы сообщить бэкенду результат платежа.
 * Платёжный сервис регистрирует результат платежа на основании полученного webhook.

### **Сверка данных**
В предыдущем разделе рассмотрен штатный сценарий проведения платежа. Ошибочные сценарии выявляются и устраняются с помощью фонового процесса сверки.

Каждую ночь PSP отправляет файл взаиморасчётов, с помощью которого наша система сравнивает состояние внешней системы с состоянием внутренней.

<div style="margin-left:3rem">
    <img src="./images/settlement-report.png" alt="отчёт о взаиморасчётах" width="500" />
</div>

Этот процесс также позволяет обнаруживать внутренние несоответствия, например между главной книгой и сервисом кошелька.

Несоответствия обрабатываются финансовой командой вручную. Они могут быть:
 * классифицируемыми: известные несоответствия, которые можно исправить по стандартной процедуре;
 * классифицируемыми, но не поддающимися автоматической обработке: их вручную исправляет финансовая команда;
 * неклассифицируемыми: финансовая команда вручную расследует и исправляет их.

### **Обработка задержек при проведении платежей**
Иногда проведение платежа занимает несколько часов, хотя обычно на это уходят секунды.

Это может произойти, если:
 * Платёж помечен как высокорисковый и требует ручной проверки.
 * Кредитная карта требует дополнительной защиты, например 3D Secure Authentication, для которой нужно запросить у держателя карты дополнительные данные.

Такие ситуации обрабатываются следующим образом:
 * Мы ждём webhook от PSP о завершении платежа либо опрашиваем его API, если провайдер не поддерживает webhook.
 * Показываем пользователю статус «ожидает обработки» и предоставляем страницу для проверки состояния платежа. Также можно отправить ему электронное письмо после завершения платежа.

### **Взаимодействие между внутренними сервисами**
Сервисы могут взаимодействовать друг с другом синхронно или асинхронно.

Синхронное взаимодействие (например, HTTP) хорошо работает в небольших системах, но с ростом масштаба проявляются его недостатки:
 * Низкая производительность: цикл запроса и ответа становится длиннее при добавлении сервисов в цепочку вызовов.
 * Слабая изоляция отказов: если PSP или другой сервис выходит из строя, пользователь не получает ответа.
 * Жёсткая связанность: отправитель должен знать получателя.
 * Сложность масштабирования: без буфера трудно справиться с внезапным ростом трафика.

Асинхронное взаимодействие можно разделить на два типа.

Один получатель — несколько получателей подписаны на одну тему, но каждое сообщение обрабатывается только один раз:

<div style="margin-left:3rem">
    <img src="./images/single-receiver.png" alt="один получатель" width="500" />
</div>

Несколько получателей — несколько получателей подписаны на одну тему, и сообщения доставляются каждому из них:

<div style="margin-left:3rem">
    <img src="./images/multiple-receiver.png" alt="несколько получателей" width="500" />
</div>

Второй вариант подходит нашей платёжной системе, поскольку платёж может запускать несколько побочных действий, обрабатываемых разными сервисами.

Иными словами, синхронное взаимодействие проще, но не позволяет сервисам быть автономными.
Асинхронное взаимодействие жертвует простотой и согласованностью ради масштабируемости и устойчивости.

### **Обработка неуспешных платежей**
Любая платёжная система должна предусматривать обработку неуспешных платежей. Для этого можно использовать следующие механизмы:
 * Отслеживание состояния платежа: при сбое по состоянию платежа можно определить, следует ли повторить операцию или вернуть средства.
 * Очередь повторных попыток: платежи, которые нужно повторить, помещаются в неё.
 * Очередь недоставленных сообщений (dead-letter queue): окончательно неуспешные платежи помещаются в неё для отладки и проверки.

### **Доставка ровно один раз**
Чтобы не списать деньги с покупателя дважды, необходимо гарантировать обработку платежа ровно один раз.

Операция выполняется ровно один раз, если одновременно гарантируется её выполнение не менее одного раза и не более одного раза.

Для гарантии выполнения не менее одного раза воспользуемся механизмом повторных попыток:

<div style="margin-left:3rem">
    <img src="./images/retry-mechanism.png" alt="механизм повторных попыток" width="500" />
</div>

Вот несколько распространённых стратегий выбора интервалов между повторными попытками:
 * Немедленный повтор: клиент сразу же повторяет запрос после сбоя.
 * Фиксированный интервал: перед повтором платежа выдерживается заданная пауза.
 * Постепенное увеличение интервала: пауза между каждой следующей попыткой увеличивается.
 * Экспоненциальная задержка: интервал между следующими попытками удваивается.
 * Отмена: клиент отменяет запрос. Это происходит при окончательной ошибке или достижении предельного числа попыток.

Как правило, по умолчанию следует использовать экспоненциальную задержку между повторными попытками. Рекомендуется, чтобы сервер указывал интервал повтора в заголовке `Retry-After`.

При повторах сервер может обработать платёж дважды:
 * Клиент дважды нажимает кнопку «Оплатить», и с него дважды списывают деньги.
 * PSP успешно проводит платёж, но последующие сервисы (главная книга, кошелёк) его не обрабатывают. При повторе PSP проводит тот же платёж ещё раз.

Чтобы избежать повторного списания, нужно использовать механизм идемпотентности: операция, применённая несколько раз, обрабатывается только один раз.

На уровне API клиент может выполнить несколько вызовов, и все они дадут одинаковый результат.
Идемпотентность обеспечивается специальным заголовком запроса (например, `idempotency-key`), значением которого обычно служит UUID.

<div style="margin-left:3rem">
    <img src="./images/idempotency-example.png" alt="пример идемпотентности" width="500" />
</div>

Идемпотентности можно добиться с помощью ограничений уникальности в базе данных:
 * Сервер пытается добавить в базу данных новую строку.
 * Вставка завершается ошибкой из-за нарушения ограничения уникальности.
 * Сервер распознаёт эту ошибку и вместо этого возвращает клиенту уже существующий объект.

Идемпотентность также обеспечивается на стороне PSP с помощью nonce, о котором говорилось ранее. PSP гарантирует, что платежи с одинаковым nonce не будут проведены повторно.

### **Согласованность**
На протяжении жизненного цикла платежа вызываются несколько сервисов с состоянием: PSP, главная книга, кошелёк и платёжный сервис.

Взаимодействие между любыми двумя сервисами может завершиться сбоем.
Реализовав обработку ровно один раз и сверку данных, можно обеспечить eventual consistency между всеми сервисами.

При использовании репликации придётся учитывать её задержку: пользователи могут увидеть несогласованные данные в основной базе данных и репликах.

Чтобы избежать этой проблемы, можно выполнять все операции чтения и записи в основной базе данных, используя реплики только для резервирования и переключения при отказе.
В качестве альтернативы можно поддерживать синхронность реплик с помощью алгоритма консенсуса, например Paxos или Raft.
Также можно использовать распределённую базу данных на основе консенсуса, например YugabyteDB или CockroachDB.

### **Безопасность платежей**
Для обеспечения безопасности платежей можно использовать следующие механизмы:
 * Перехват запросов и ответов — защитить всё взаимодействие с помощью HTTPS.
 * Подмена данных — использовать шифрование и контроль целостности.
 * Атаки типа «человек посередине» — использовать SSL с закреплением сертификата.
 * Потеря данных — реплицировать данные в нескольких регионах и создавать снимки.
 * DDoS-атака — внедрить ограничение частоты запросов и межсетевой экран.
 * Кража данных карты — использовать токены вместо хранения настоящих данных карты в системе.
 * Соответствие PCI — соблюдать стандарт безопасности для организаций, работающих с банковскими картами международных платёжных систем.
 * Мошенничество — проверять адрес и значение проверки карты (CVV), анализировать поведение пользователей и т. д.
